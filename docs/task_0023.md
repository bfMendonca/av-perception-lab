# Task 0023: Model readiness states and Prepare actions in the web UI (COMPLETED)

## Description

`task_0022` gave the web server the readiness API (`POST /api/models/status`,
the Prepare queue with SSE progress, 409 on a run whose models are not ready),
but the interface shows none of it: a freshly cloned repository loads a sample
YAML, the cards look fine, and Process ends in a 409 the user cannot act on.
This task adds the interface side of "Prepare model" (spec
`docs/superpowers/specs/2026-10-31-model-readiness-design.md`, goal 7 and
"UI"; mockup `docs/superpowers/specs/mockups/model-readiness-mockup.html`,
direction only):

- `useModelStatus(config)`: debounced status request for the edited
  pipeline, rows keyed by `{stage, index}`, request races handled like the
  validation (a sequence bumped on schedule);
- card states on the pipeline flow (user's spec): *ready* stays solid; a model
  that is not ready gets a **yellow dashed outline and a small alert icon at
  the top-right corner**; *preparing* shows a progress bar fed by the SSE
  events; *failed* is red dashed with the reason; *conflict* (and any state
  this UI does not know) uses the not-ready warning style with its message;
- `ReadinessBanner`: "N models need preparing · X GB" with **Prepare all**,
  shown only when something needs preparing;
- inspector section "Weights & requirements": layers, missing items, the
  server's message (source / reason), size, licence and target folder when
  the row exposes them, **Prepare model** (or **Retry**), a pointer to the
  module's path options to override the location, and — for an unknown source
  the web may not download — the hint with a copyable
  `det-depth-distance --config <file> --prepare` command instead of a button;
- Process disabled with a reason while any model is not ready, enabled when all
  are ready; a 409 from the server lists the models that are not ready.

The UI stays generic: no model, stage or source name in `web/src`; unknown
states render with the generic style.

## Impact Analysis

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Status requests flood the server while typing | Medium | Debounced; stale responses dropped by sequence |
| Process blocked by a stale or unavailable status | Low | Only a successful status blocks; unavailable/pending never blocks (the server still answers 409) |
| Model names creeping into the UI | Low | Everything comes from the rows; tests use fake names only |
| A failed Prepare reverting to plain "missing" after the refresh | Medium | Failures of the last attempt are kept per model until it is retried or becomes ready |
| Existing tests break on the new requests | Medium | Fake models API in fixtures; the hook tolerates an unreachable API |

## Implementation details

- `api/models.ts`: types of the status rows (`ModelState` is open: any string),
  `PrepareJob`, `PrepareEvent`; `createModelsApi` (status, prepare, job,
  cancel, SSE via `EventSource`, closed on `end` like the jobs stream); a 422
  with `errors` becomes `StatusRejected`.
- `models/useModelStatus.ts`: `useModelStatus(config, {api, debounceMs,
  notify})`. The config is compared by its JSON text; each change bumps the
  sequence and schedules a request after `debounceMs` (the editor store's
  value, 0 in tests); an answer whose sequence is no longer current is
  dropped. Status `ready | pending | invalid (422) | unavailable (other
  error)`; the last rows stay on screen while pending (no flicker). Prepare:
  POST, then follow the job's SSE: `model` events with an active state mark
  the model `preparing`/`queued`; `progress` events accumulate bytes per item
  (fraction = Σdone/Σtotal, null when a total is unknown); a final `model`
  event stores the attempt (failed/missing with its message; ready or
  cancelled clear it); `end` closes the stream and refreshes the status. The
  view overlays: local progress > attempt (keeps `failed` with its reason
  after the refresh, dropped when the type/name changes or the row is ready)
  > server row. A model already ready is never shown as preparing (a "Prepare
  all" no-op). While the server reports `preparing` for a job this page did
  not start, it polls every 2 s. `ReadinessProvider` / `useReadiness()` share
  it (null outside: components render as before).
- Cards: `ModuleCard` gets a `readiness` prop (`cardReadiness(rows)`, the
  worst row decides): `card--notready` (missing, conflict, any unknown state:
  yellow dashed outline + `.card__alert` badge `role="img"` at the top-right,
  its name the state and message), `card--preparing` (yellow dashed +
  `role="progressbar"` with `aria-valuenow` in percent and an `aria-valuetext`
  "2.0 MB of 8.0 MB"; indeterminate when queued or without totals),
  `card--failed` (red dashed + red badge), `card--ready` (solid, nothing
  added). A state line shows the label and "690 MB to download" or the first
  clause of the reason. `data-model-state` carries the raw state.
- Rows map to slots by `{stage, index}`; a single-slot stage also takes rows
  of its sub-paths (`<stage>.<part>`), so a model under a general section
  shows in that section's settings tab.
- `ReadinessBanner` (above the lanes): "N models need preparing · X GB" where
  X is the declared size of the models Prepare all would download (the
  server's `total_size_bytes` also counts an unknown source, which the web
  cannot fetch, so the banner sums the preparable rows instead); a "Show
  models" list whose items select the model's card or settings tab; Prepare
  all (`models: "all"`, disabled when nothing is preparable); while preparing,
  an overall bar (queued models count with their declared size) and Cancel;
  "Check again" when the status is unavailable; hidden when all are ready.
- `ModelRequirements` ("Weights & requirements"): per row the where/state
  header, the message (`role="alert"` when failed), layers, missing items,
  size, source / licence / target when a row carries such fields (it does not
  today), else the `<weights root>/...` locations parsed from the server's
  message; **Prepare model** or **Retry** for preparable rows (not ready, not
  preparing, not conflict, not an unknown source, not only `package:` items);
  for an unknown source (message prefix `unknown source`) the explanation and
  a copyable `det-depth-distance --config <file> --prepare`; a note when only
  packages are missing and when in conflict (Task 6 adds "Install packages"
  next to it); the override pointer names the module's path options left
  unset by default, preferring one named like a missing item. A module
  without a status row gets no section; a ready one gets a one-line "nothing
  to prepare" and no button. Shown before Options when something needs work,
  after them otherwise.
- Process: `readinessBlock` adds "N models are not ready — Prepare them
  first." (or "Preparing N models: …") to the existing reasons; an
  unavailable or invalid status never blocks (the server still answers 409).
  `submitRun` throws `ModelsNotReady` on a 409 with `models_not_ready`;
  `useProcess` opens the "Models not ready" dialog (list with where, name,
  state, message; Close and Prepare all) and refreshes the status. A rerun's
  409 shows the list in the notice (`notReadyText`).
- `statusStyles.css` repeats a theme class in its selectors (`.card.card--…`,
  `.btn.btn--warn`, `.progress.progress--model`): it may load before
  `theme.css`, which would otherwise win at equal specificity (seen in the
  browser check: the dashed outline was lost).
- The existing guard `tests/web/test_extensibility.py` caught stage names in
  doc comments; they were rewritten as `<stage>`.
- Deviation: the implementation was written before the tests (not strict
  test-first). Red phase checked afterwards: with the wiring of `Lanes`,
  `Inspector` and `useProcess` reverted, 13 of the new tests fail.

### Review fixes (round 1)

- I1, no flash of "Not ready" mid-job: a model whose final `model` event is
  `ready` keeps a "finished" overlay (identity + the status sequence at that
  moment) and shows ready until a status answer to a request made after it
  arrives; an in-flight older answer does not clear it.
- I2a, re-attach: `GET /api/models/prepare` (new, `PrepareQueue.recent()`,
  newest first, same shape as the job route) is read on mount and while the
  server reports `preparing` for a job the page does not follow; every
  queued/running job is followed over SSE (the server replays its events), so
  progress, `busy` and Cancel work after a reload. A model queued in such a job
  but `ready` on the server is shown ready.
- I2b, replays: per item `done` keeps the maximum (never rewinds); a model
  whose final event was seen in a job ignores later `queued`/`preparing`/
  `progress` events of that job; a replayed `queued` never takes a running
  model back.
- I3, identity: every overlay (preparing, finished, attempt) carries type +
  name and applies only to a row with that identity; a preparing overlay of a
  moved module follows it (unique match in the same stage). Rows are also
  filtered by `rowMatchesConfig` against the edited config (a key the config
  sets: type, name when the spec sets one, index in range; unset keys and
  sub-paths are kept), so between an edit and the next answer old rows never
  land on another card.
- I4+I5, server fields: rows carry `source` (each kind's
  `describe_source()`: "Hugging Face · <repo>", the URL host, "git · <url>",
  the user-provided hint, default the kind name), `license`, `target`
  (weights-root-relative, "; "-joined), `reason` (`unknown_source`,
  `packages_only` or null) and `preparable` (state `missing` and no reason;
  false while preparing). All redacted. The UI uses them (inspector Source,
  Licence, Stored in `<weights root>/<target>`; banner "Licences: …" and the
  Prepare all tooltip with size and licences) and keeps the message-prefix /
  `package:` / path-regex logic only for rows without the fields.
- I6: banner headline "N models need preparing · X to download" counts only
  preparable models (else "N models are not ready"); the others stay in the
  "cannot be prepared from here" sub line.
- Trivial: JSX inside `<ReadinessProvider>` (App.tsx) and the dialog fragment
  (useProcess.tsx) reindented; `.reqs__layers` lost its `!important`.
