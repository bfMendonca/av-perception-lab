# Task 0022: Web API for model status, prepare queue and run gating (COMPLETED)

## Description

`task_0019`–`task_0021` declare what every model needs, check it without
torch and obtain it with `--prepare`. The web server does not know about any
of it yet: a run with missing weights is queued and fails deep in `load()`,
and the UI has no way to show readiness or start a download. This task adds
the server side of "Prepare model" (spec
`docs/superpowers/specs/2026-10-31-model-readiness-design.md`, "Engine and
API", "Security", "A pipeline with a not-ready model"):

- `POST /api/models/status` — readiness of every model a config would load,
  computed exactly like `--prepare` builds them (`cli.config_requirements`),
  never loading a model nor importing torch;
- a `PrepareQueue` (one Prepare at a time, independent from the GPU
  `JobQueue`) with routes to submit, inspect, follow (SSE, per-model progress)
  and cancel a Prepare; the engine runs in a worker thread so the event loop
  stays responsive;
- `POST /api/runs` (and rerun) answers 409 `{models_not_ready: [...]}` when a
  model of the config is not ready;
- `--weights-root` server flag (and `DDD_WEIGHTS_ROOT`), validated against the
  client-writable roots;
- the path check of run configs (`security.path_problems`) resolves a field
  the way its adapter does (YOLO / Ultralytics SAM bare weight names live
  under `<weights root>/ultralytics/`), and the weights root counts as an
  asset root, so every shipped config passes an `--asset-root` check.

## Impact Analysis

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Older web tests submit configs whose models are not ready | High | Autouse fixture marks models ready; the gating tests opt out |
| A client steers a download (URL, path) | Low | Bodies are `extra="forbid"`; sources and targets come from adapter code; targets are contained in the weights root |
| Absolute server paths leak in messages | Medium | The weights root is replaced by `<weights root>` in every message sent |
| Cancel leaves a second writer on the same files | Low | The next job starts only after the worker thread returns (sources check the event between chunks) |
| Status blocks the event loop (git, file walks) | Medium | Computed in the thread pool |

## Implementation details

- `web/models.py`: `config_rows(config)` = `cli.config_requirements` on
  `config.config_from_mapping` (the exact `--prepare` path; `cli` imports no
  torch), keyed `(stage, index)` by splitting the config path
  (`detectors[1]` -> `("detectors", 1)`, `depth`/`camera.estimate` -> index
  `None`). `status_row` = `check(req, root)` (an unsafe declaration is a
  `failed` row). `report` adds `total_size_bytes` (declared sizes of models not
  ready). `redact` replaces the weights root (as given and resolved) with
  `<weights root>` in every message.
- `PrepareQueue(weights_root)`: `submit(models | "all", config)` resolves the
  rows at submit time (`UnknownModel` for a key not in the config, ValueError
  for an empty selection); a single runner task awaits
  `asyncio.to_thread(prepare, req, root, progress, cancel_event)` per model.
  Progress is throttled in the calling thread (0.2 s per item, the first and
  last always sent) and handed to the loop with `call_soon_threadsafe`; events
  are appended on the loop thread only and subscribers wake on a per-job
  `asyncio.Event` that is replaced at each append. Cancellation sets the job's
  own `cancel_requested` flag plus the engine's `threading.Event` (the
  message of `prepare` is never parsed); a queued job ends at once, a running
  one when the engine returns, and only then does the next job start (no two
  writers on the same files). The job ends `cancelled`, `failed` (any model
  not ready, error = `"<stage[index]> <name>: <message>"` joined) or `done`.
  `preparing()` gives the requirement being worked on; the status endpoint
  and the run gate show it as `preparing`. Nothing is persisted: the 20 latest
  finished jobs stay in memory; results are logged (`logging`).
- `web/app.py`: routes `POST /api/models/status`, `POST /api/models/prepare`,
  `GET /api/models/prepare/{id}`, `GET .../events`, `DELETE
  /api/models/prepare/{id}`; bodies are pydantic models with
  `extra="forbid"`. `submit_run` became `async`: after the 422 checks it
  computes the statuses in the thread pool and answers 409
  `{models_not_ready}`. Prepare applies the same 422 checks as a run
  (`validate_config` + `path_problems`). `create_app` takes the weights root
  from `weights_root()` and refuses one overlapping the client-writable
  roots. The lifespan cancels the prepare queue first. The stale comment of
  `yaml_expanded_nodes` (shipped configs sharing `hf_cache` through an
  anchor) now says a hand-written config may use one.
- `web/server.py`: `--weights-root` -> `set_weights_root`; absent, the
  `DDD_WEIGHTS_ROOT` / `weights/` default applies; the resolved root is
  checked with `security.weights_root_problem` (parser error, exit 2).
- `web/security.py`: `weights_root_problem` (the root may not be, contain or
  lie inside the library or out_root); `path_problems` appends the weights
  root to the asset roots when `--asset-root` is set.
- Path resolution like the adapter (controller ruling): instead of naming
  YOLO under `web/`, a `Path` option may carry `core.options.PATH_RESOLVER`
  field metadata (`field(metadata={PATH_RESOLVER: resolve_weights})` on the
  YOLO and Ultralytics SAM `weights`), and `schema.config_paths` reports the
  resolved path. The adapter helper is reused, not re-implemented, and a
  future adapter with the same need declares it on its own field. Without it,
  7 shipped configs failed an `--asset-root` check; with it all 16 pass.
- `schema._split_error` became `schema.split_error` (used by the app for a
  `ConfigError` raised while building the rows).
- Tests: `tests/web/model_fakes.py` (fake detector `gate` with one
  `GateAsset` per option `blob`, a `GateSource` that writes, blocks until
  released/cancelled, or fails offline; DA3 with an `hf_cache` outside the
  root and `camera.estimate: null` so only the gate assets matter; packages
  treated as installed). The autouse `models_ready` fixture of
  `tests/web/conftest.py` lifts the gate for the older run tests;
  `test_models_gating.py` overrides it.
- Deviation: the implementation was written before most of the new tests
  (not strict test-first); the tests were then checked against the behaviour
  (e.g. the shipped-config test fails for 7 configs with the resolver
  disabled).

### Review fixes (round 1)

- I1, known sources only: `Asset.known` (core, default True, set by the
  adapter's code). `adapters/_hf_hub.hf_asset` sets `known = repo in
  HF_FACTS`, so a repo typed in `depth.model` (DA3), `refiners[i].model` (HF
  SAM family) or `semantic[i].model` (SegFormer) that the project does not
  ship is unknown. `web/models.unknown_sources` lists the unknown assets that
  are not ready; `status_row` turns such a model into `missing` with the
  message "unknown source: prepare it from the CLI (--prepare)" (so a run is
  409). `PrepareQueue.submit` raises `UnknownSource` (422) for a named one;
  with `models: "all"` the known models are queued and the unknown ones are
  reported in the job's `skipped` (422 only if every model is skipped). The
  engine ignores `known`: the CLI `--prepare` downloads any repo. Revisions are
  not pinned (out of scope this round).
- I2, redaction: `core.requirements.redact_root(text, root, label)` (also
  used by the CLI gate) replaces only the absolute forms of the root
  (`absolute()` and `resolve()`), at a path boundary, in one regex pass; a
  relative root (`--weights-root weights`) no longer rewrites the asset key
  `weights`, the label is never re-substituted, and `weights-old` is left
  alone. `web.models.redact` delegates to it. The exception text caught in
  `PrepareQueue._run_forever` is redacted too.
- CLI gate (plan gap): `cli.require_ready(cfg)` runs in `cli.run` after every
  configuration error (component specs, camera, Pipeline construction) and
  before `resolve_intrinsics` / `load`: every row of `config_requirements` is
  checked; any not ready raises `ConfigError` (exit 2) listing
  `<path> <name> (<type>): <what is missing>` (root-relative) and naming
  `--prepare`. Explicit paths outside the root are not declared, so not
  checked. `tests/smoke/smoke_fakes.install_scene_fakes` makes the fake DA3
  (and the focal model) declare no requirement, since its network is fake;
  without it the smoke tests would depend on the author's `weights/hf`.
