# Task 0025: Document model readiness and the conflict resolution paths (COMPLETED)

## Description

Tasks 0019–0024 built model readiness: every component declares what it needs
(`requirements(options)`: assets, code, packages), the CLI prepares it
(`--prepare`, `--install-packages`), the web server reports and prepares it
(status rows, Prepare model, Prepare all, Install packages) and dependency
conflicts are detected before anything is installed. The design
(`docs/superpowers/specs/2026-10-31-model-readiness-design.md`,
"Documentation deliverables") asks for English documentation that a friend who
clones the repository, and a developer who adds a model, can follow without
reading code:

- a new `docs/model_environments.md`: the model "recipe" format with a worked
  example of adding a model (a hypothetical Metric3D depth model), the three
  layers and asset kinds, default locations and overrides, the states and how
  the UI draws them, the CLI and the web flows, the packages layer, and
  **each dependency-conflict resolution path in detail** — (1) detect before
  installing (implemented), (2) mutually exclusive extras via
  `[tool.uv] conflicts`, (3) one environment per profile used by the worker
  subprocess, (4) the conflicting model served as its own process, (5) manual
  pinning or forking — with when to use each, cost, limits and how it would
  plug into this design (2–5 clearly marked as not implemented);
- README: the "Model weights" section reworked as an English quick path
  (clone, base stack, load a sample, Prepare; CLI `--prepare`;
  `--weights-root`; gated models; the manual TwinLiteNet+ step) and a TODO
  entry for paths 2–5 linking to the new document;
- `DESCRIPTION.md`, `CHANGELOG.md` and `docs/web_extending.md` (a section on
  requirements for new models: no web edits needed).

Every command, flag, route and field named in the documents is verified
against the code; a statement that cannot be verified is changed in the
document, not in the code.

## Implementation details

- **What was done.** `docs/model_environments.md` (new, English): the recipe
  (`requirements(options)` and the three layers), asset kinds and their rules
  (HF cache layout and revision names, the URL `size_bytes`/`sha256` rule,
  `UserProvided`, `CodeRepo` 7–64 hex pin), registering a new source kind
  (Google Drive as the sketch; not in v1), the weights root and locations
  (bare-name rule and the `./name.pt` edge), the states and their drawing,
  the CLI (`--prepare` exit codes 0/1/2/130, `--install-packages`, the gate
  with exit code 2) and the web (status body, Prepare model / Prepare all,
  unknown sources, gated models and `HF_TOKEN`, the manual TwinLiteNet+ step),
  the packages layer (base stack, detect, dry-run, install, `uv.lock` and
  `--locked`, `DDD_UV`, failed vs conflict, installs vs runs, restart), a
  worked Metric3D example and the five conflict-resolution paths (path 1
  implemented; 2–5 marked NOT implemented, each with when to use it, cost,
  limits and what would change). README: "From a fresh clone" steps in
  "Model weights", gated models, TwinLiteNet+, older machines; TODO entries
  for task_0024 (missing until now), task_0025 and the open paths 2–5.
  `docs/web_extending.md`: section (e), in English. `DESCRIPTION.md`: the
  `docs/` tree line and a conventions line. `CHANGELOG.md`: an entry.
- **How claims were verified.** Every symbol, flag, route and field was read
  in the code (`core/requirements.py`, `core/provision/*`, `adapters/_weights.py`,
  `_hf_hub.py`, `_ultralytics.py`, `twinlitenet.py`, `cli.py`,
  `web/{app,models,server,jobs}.py`, `web/src/models/*`,
  `web/src/editor/ModuleCard.tsx`). The Metric3D example was written as a
  real module in a scratch folder and loaded next to the real registry (no
  download, no load, empty scratch weights root): `requirements()`, `check()`,
  `plan_packages()`, the catalog hints, `--list-models` and a
  `POST /api/models/status` through `TestClient` gave what section 7.4 says.
  The packages outcomes were checked with a scratch copy of `pyproject.toml`
  declaring `model-metric3d` and two fake `uv` executables (missing: plan
  `error`; resolver failure: plan `conflict`). No real `uv sync`, no
  download, no GPU.
- **Deviations from the plan.** (1) The CLI has no `--weights-root` flag (only
  the web server does): the documents say `DDD_WEIGHTS_ROOT` for the CLI and
  recommend exporting it so the web worker subprocess sees the same root (it
  inherits the server's environment; `--weights-root` alone sets it only in
  the server process). (2) The spec's `weights/<family>/<model>/` convention
  is documented as it is implemented: a folder per family (`rfdetr/`,
  `ultralytics/`, `hf/`), with a sub-folder per model where a family needs it
  (the Metric3D example). (3) The uv message for declared `[tool.uv]
  conflicts` is described, not quoted (verifying it needs a real `uv sync`).
  (4) `docs/web_extending.md` is pt-BR; the new section (e) is English, the
  rest is not migrated.
- **Notes.** `restart_required` does not block runs on the server (only the UI
  note asks for a restart); the documents say so. The `./name.pt` edge and
  the unpinned Hugging Face revisions remain as documented behaviour.
