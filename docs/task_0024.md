# Task 0024: Packages layer with dry-run conflict detection (COMPLETED)

## Description

Every component declares a packages layer (`Requirements.packages`, the import
names, and `Requirements.extra`, the `pyproject.toml` extra that provides
them; task_0019), but nothing acts on it: `--prepare` and the web Prepare
report missing packages and stop. The design
(`docs/superpowers/specs/2026-10-31-model-readiness-design.md`, "Packages
layer in v1" and "Calls made after the builder check") asks for: detect,
dry-run, then install only after explicit confirmation, and never remove the
existing stack.

This task adds `core/provision/packages.py`:

- `detect_extras(pyproject)`: the extras of `[project.optional-dependencies]`
  whose distributions are installed (`importlib.metadata`) and whose import
  names (declared by the components) are found by `find_spec`, without
  importing anything;
- `dry_run(extra, detected)`: `uv sync --dry-run` with `--extra` for every
  detected extra plus the new one (never a bare `uv sync`, never a removal);
  the result carries the resolver's reason;
- `install(extra, detected, ...)`: the same command without `--dry-run`,
  streaming output, cancellable (process group killed);
- a plan per component: base stack missing (the `infer` extra; the server and
  the CLI never install it, they print `uv sync --extra infer --extra web`),
  a per-model extra whose dry-run is clean (installable after confirmation) or
  a conflict (new model state `conflict` with the resolver's reason and a
  pointer to `docs/model_environments.md`).

The web gains the **Install packages** action (a Dialog stating the exact
command, run as a Prepare job whose `uv` output streams into the events, then
"restart the server"); a missing base stack shows the one-time command with a
copy button instead of a button. The CLI gate names `uv sync --extra infer`
when only packages are missing, and `--prepare` reports the packages plan;
`--prepare --install-packages` runs the clean dry-run and then the install.

## Impact Analysis

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| An install rewrites or shrinks the shared GPU environment | Medium | Never a bare `uv sync`: every detected extra is passed, plus `--inexact` (nothing extraneous is removed) and `--locked` (the lock is not rewritten); a dry-run that would uninstall or replace a package is a conflict; the base extra is never installed by the server or the CLI |
| Detection runs package code | Low | Only `importlib.metadata` and top-level `find_spec` |
| The status route gets slow (a `uv` call per request) | Medium | Dry-runs only for a per-model extra that is missing, cached per (extra, detected extras, pyproject/lock mtimes) |
| A test calls the real `uv` | Low | Every test injects a fake; the default is resolved only when no fake is given |

## Implementation details

- `core/provision/packages.py` is stdlib only (`tomllib`, `importlib.metadata`,
  `subprocess`; `packaging.markers` only if available, for requirement
  markers). `detect_extras` keeps an extra when every distribution of
  `[project.optional-dependencies]` has metadata and every import name the
  components declare for it (`imports_of(reqs)`) is found by the top-level
  `find_spec` (`requirements._top_level_present`); `importlib.invalidate_caches()`
  runs first so an install made by this process is seen.
- The command is `uv --color never sync --locked --inexact --extra <each
  detected extra and the new one, sorted> [--dry-run]`, run in the project
  folder with `NO_COLOR=1` and, when the caller has not set it,
  `UV_PROJECT_ENVIRONMENT=sys.prefix` (the environment that was inspected is
  the one that changes). Extra names must be PEP 685 normalised names (no
  option can be injected). **Additions to the brief**: `--inexact` (nothing
  extraneous is removed even if detection missed an extra or a dependency
  group) and `--locked` (the lock is never rewritten by the server; a lock
  that does not cover the new extra fails the dry-run with uv's reason). A
  dry-run whose plan has `- name==version` lines (an uninstall or a version
  replacement) is reported as not clean: "would remove or replace installed
  packages ...; the environment is left untouched".
- `resolver_reason` keeps uv's output from the first `error`/`×` line,
  drops progress lines and ANSI codes, and caps it at 1500 characters;
  `relative()` shows the project folder as `.` and the home as `~`; the web
  also redacts the weights root.
- `plan_packages(req)`: `ready`; `base` for the base extra (`BASE_EXTRAS =
  {"infer"}`) or for a per-model extra while the base stack is not detected
  (command `uv sync --extra infer --extra web`, never run; no uv call);
  `invalid` for no extra or an extra the pyproject does not declare;
  otherwise a dry-run (cached per extra, detected extras, uv, pyproject and
  `uv.lock` mtimes, 32 entries; `fresh=True` bypasses it) -> `install` or
  `conflict` (message names `docs/model_environments.md`).
- `engine.install_packages(req, on_line, cancel)`: fresh plan; only
  `install` runs `packages.install` (base extra, missing base stack and
  undeclared extras are refused again inside `install`); returns
  `PackagesOutcome(status, plan, installed)`; never raises for uv failures
  (state `failed` with uv's reason; cancel -> message starting with
  "cancelled"). `with_package_plan` maps `conflict` -> state `conflict` and
  `invalid` -> `failed` when the model was `missing`.
- `install` runs uv with `start_new_session=True`; a reader thread streams
  merged stdout/stderr to `on_line`; cancel (polled every 0.2 s) and the
  1-hour timeout `killpg` the group with SIGKILL, like the git source.
- Web: `status_row(row, root, imports)` computes the plan only when the
  packages layer is not ready (so a configured base stack costs no uv call);
  rows gain `packages` (`plan_view`). `PrepareQueue.submit(..., packages=True)`
  needs named models (not "all") and refuses with `NotInstallable` (422) a
  model whose extra is the base stack or absent; the job has
  `kind: "packages"` and runs `install_packages` in a worker thread, output
  lines go through `call_soon_threadsafe` as `output` events (redacted, at
  most `OUTPUT_LIMIT` = 2000 per job). A packages job succeeds when the
  packages layer is ready (weights may still be missing). After a completed
  install `PrepareQueue.restart_required` is set and returned by
  `POST /api/models/status` (`restart_required`).
- CLI: `require_ready` adds a hint per kind of problem — files ->
  `--prepare`; base packages -> `` `uv sync --extra infer` `` (add
  `--extra web` for the server) and "--prepare does not install packages";
  per-model extra -> `--prepare --install-packages`. `prepare_command(cfg,
  root, install)` adds the packages plan per model (notes, `conflict` in
  the state column); `--install-packages` (only with `--prepare`) runs the
  install and prints uv's lines as `[uv] ...`. This covers the final-wave
  item 3 of the plan (gate message for packages-only).
- UI: `ModelRequirements` shows, from `row.packages`, the base command with
  `CopyCommand`; **Install packages** (only for `install`) opening a `Dialog`
  that states the extra, the exact command, that nothing is removed, that the
  server re-runs the dry-run first and that a restart is needed; the conflict
  note with `docs/model_environments.md`; "Installing packages…" and the last
  8 `uv` lines while the job runs. `useModelStatus` gains `installPackages`
  and `restartRequired` (from `restart_required` or a model event with
  `installed: true`); `ReadinessBanner` shows "Packages were installed on the
  server · Restart the server to use them" even when everything is ready. The
  older `packages_only` note stays for servers without `packages`.
- Tests: a fake `uv` script (`tests/fake_uv.py`) records arguments, cwd and
  `UV_PROJECT_ENVIRONMENT`; in `conflict` mode it would modify the
  environment directory if it ran without `--dry-run`, so the before/after
  snapshot proves only a dry-run ran. The test site folder has a `fakebase`
  package whose import raises (detection must not import it).
- Code was written before the tests (not strict TDD); the tests were run
  against the implementation afterwards and adjusted where they encoded a
  wrong expectation (an already installed package makes a second install a
  no-op; uv output lines keep their leading indentation).

### Review fix round 1

- I1: `DryRunResult.kind` (`ok`, `resolver`, `replace`, `invalid`,
  `unavailable`, `timeout`, `cancelled`). uv not found / not executable and a
  timeout (and a cancel) are `TRANSIENT`: plan action `error` -> state
  `failed` with a readable message (the unavailable one names `DDD_UV`),
  never `conflict`, never cached.
- I2: `cached_dry_run` is single flight (one `Future` per key in
  `_INFLIGHT`; concurrent callers share it). `dry_run` runs uv with
  `start_new_session=True` and, on timeout or cancel, kills the group and
  closes the pipes (a grandchild holding the pipe cannot block). The job's
  fresh dry-run honours the job's cancel event (`plan_packages(...,
  cancel=)`). `DRY_RUN_TIMEOUT_S` is read at call time.
- I3: `PrepareQueue.installing()` and `JobQueue.active()`. `POST
  /api/models/prepare` with `packages: true` answers 409 while a run is queued
  or running; `POST /api/runs` (and rerun) answers 409 `{detail,
  packages_installing: true}` while an install is queued or running. Both
  checks run after the route's awaits, right before queueing.
- I4: the route computes the server-side plans first
  (`PrepareQueue.install_plans`, config-wide import names, in the
  threadpool); `submit(..., packages=True, plans=)` requires each plan to be
  `install` (422 with the plan's reason for `base`, `conflict`, `error`,
  `ready`). The job passes the same `imports` and `expected=plan` to
  `install_packages`, which runs nothing unless the fresh plan is `install`
  with the same extras and command ("the environment changed since the
  install was confirmed ..."). The CLI also uses config-wide import names for
  both plans.
- Credentials: `packages.scrub` (`scheme://user:pass@` -> `***@`,
  token/password/secret/key/sig/auth query values, `Bearer|token|basic
  <value>`, `hf_`/`ghp_`/`glpat-`/`pypi-` tokens) runs inside `relative()`, so
  dry-run reasons and every install output line are scrubbed.
- Covering tests: `tests/test_provision_packages.py`
  (`test_uv_missing_is_an_error_not_a_conflict_and_never_cached`,
  `test_dry_run_timeout_is_not_cached_and_kills_a_hanging_grandchild`,
  `test_dry_run_cancel_stops_uv`, `test_concurrent_checks_share_one_dry_run`,
  `test_scrub_removes_credentials`,
  `test_install_refuses_a_plan_other_than_the_confirmed_one`),
  `tests/web/test_models_packages.py`
  (`test_uv_unavailable_row_is_failed_not_conflict`,
  `test_concurrent_status_requests_run_one_dry_run`,
  `test_install_refused_while_a_run_is_active`,
  `test_run_refused_while_packages_install`,
  `test_broken_base_is_never_installed_even_by_a_direct_call`,
  `test_install_job_uses_the_plan_the_status_showed`; a conflict install is
  now refused with 422 at submit), vitest "a dry-run that could not run ...".
